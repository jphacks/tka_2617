# 0006 服の寸法からシェイプキーの値をブラウザで計算する

日付：2026-10-10

## 背景

服の3Dモデルを、着丈・身幅・肩幅・袖丈のcmで指定した形にしたい。Tシャツのモデルには、部位ごとのシェイプキー（`length`、`width`、`shoulder`、`sleeve`）を、値1で1cm変わるように作った。ただ、キー同士が連動する（`width`を上げると肩幅も広がる、など）ので、「着丈を+4.5cmしたいから`length`を4.5」では合わない。

Blenderでは、目標の寸法からキーの値を求める処理（solveKeys）を作り、GUのL（70／54／47／21cm）で4.52／3.20／−1.69／−4.34になることを確かめた。

## 決定

- Blenderから、glbと一緒に計測データのjsonを書き出す。中身は、キーの名前、基準の寸法、連動を打ち消す逆行列、計測線の頂点の座標、キー値1あたりの頂点の移動量、部位ごとに長さを足す辺
- ブラウザで、このjsonを使ってsolveKeysを解く（`apps/web/src/lib/solve-keys.ts`）（その後、身長ごとの表で解く方式（[0008](0008-height-keys-and-tables.md)）に置き換え、`solve-keys.ts`とjsonは消した）
  1. 逆行列で、キー値の見当をつける
  2. その値で計測線の長さを測り、目標とのずれの0.5倍ずつキー値を直す
  3. ずれが全部位で0.01cm未満になるまで繰り返す（最大50回）
  4. キー値は、シェイプキーを作ったときのRange（−10〜20）に収める
- jsonのキーの並びとglbのモーフターゲットの並びは違うので、番号ではなく名前で対応させる
- 画面では部位ごとにcmを入力し、範囲内の数値になったときだけ形に反映する。入力できる範囲は、基準の寸法の−10〜+20cm

## 理由

- 入力するたびにその場で形が変わる。計測線の頂点は158個だけなので、繰り返しても一瞬で終わる
- サーバーが要らない。apiは3Dの処理を持たず、Supabaseにも触れない
- Blenderと同じ計算なので、Blenderで確かめた値と比べて検証できる。GUのLで4.52／3.20／−1.69／−4.34になり、検証値と一致した
- 服が増えても、glbとjsonを差し替えれば同じ処理で使える

## 代替案

- 逆行列だけで求める：繰り返しが要らないが、身幅で2.8cmずれる
- Blenderの手順どおり、0.5倍の補正を3回で止める：4.54／3.19／−1.68／−4.32になり、検証値からわずかにずれる
- サイズごとのキー値をBlenderで先に計算して表にする：任意の寸法に対応できない
- apiで計算する：入力のたびに通信が要り、3Dのデータをapiにも持たせることになる

## 影響

- 服のモデルごとに、glbと計測データのjsonを同じ.blendから一緒に書き出す必要がある。片方だけ作り直すと、キーと計測線が合わなくなる
- 計測データのjsonはBlenderが書き出したものなので、Prettierの整形の対象から外した（`.prettierignore`）
- 今は、Tシャツ1着分のjsonをコードに直接importしている。服ごとのglbとjsonや、寸法の値をどこに持つか（DBの列、別のテーブル、Storage）はまだ決めていない。決めたら`docs/er.md`と`docs/api.md`を更新する
- 値を大きく動かすと（GUのL相当で4倍ほど）、袖口や裾の輪郭がギザギザになる。布シミュレーションで作ったキーを1cm単位に縮めたときの凹凸が、引き伸ばされているのかもしれない。原因はまだ確かめていない
