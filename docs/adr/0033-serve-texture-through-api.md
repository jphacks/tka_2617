# 完成したテクスチャは、apiが推論サービスから受け取ってStorageに置き、画像のAPIで配る

日付：2026-10-17

## 背景

[ADR 0023](0023-garment-texture-on-pc.md)では、テクスチャをPC内のフォルダにだけ作り、DB・Storage・APIには出さないと決めた。アバターに服の写真の柄を貼るには、アプリからテクスチャを取れる必要がある。推論サービスはPCで動き、DBとStorageに触れるのはapiだけ（AGENTS.md）。

## 決定

アプリが`GET /v1/garments/:id/texture`で状態を聞くと、apiが推論サービスの`GET /textures/{garmentId}`に問い合わせる。完成していれば`GET /textures/{garmentId}/{job}/texture.png`で画像を受け取り、Storageの`garments`バケットに置いて、`garment_images`のrole`texture`として記録する。画像は、服の写真と同じ`GET /v1/garments/:id/images/:imageId`で配る。服の一覧と詳細の`images`には入れず、画像のIDは`GET /v1/garments/:id/texture`だけで返す。

作成中・失敗の状態は推論サービスだけが持ち、DBには完成したテクスチャだけを記録する。どの作業から作ったか（作業フォルダ名）を`texture_job`に持ち、同じ作業を2回保存しない。差し替えはDBの関数`save_garment_texture`で1つのトランザクションにする。

裏面を撮り直す前に保存したテクスチャは使わない。新しいテクスチャができるまで古い行は残るので、古いかどうかを確かめる状態のAPIだけが画像のIDを渡す。推論サービスにつながらないときは、保存済みのテクスチャがあれば返す。失敗の理由は画面に出さず、apiのログに残す。

## 理由

apiが聞きに行く形なら、推論サービスはapiのURLやトークンを持たなくてよく、apiが止まっていた間に完成したものも後で受け取れる。状態をDBにも持つと、推論サービスと食い違ったときにどちらが正しいか分からなくなる。

テクスチャは、すでに`/api/garments/:id/images/:imageId`で配っている服の写真から作る。公開の`/api/*`から新しく取られる情報は無い（[ADR 0002](0002-no-login-yet.md)）。

裏面より古いかは、テクスチャの行と裏面の行の`created_at`で比べる。どちらもDBが付けるので、推論サービスのPCと時計がずれていても比べられる。

## 代替案

- 推論サービスがSupabaseに直接置く：推論サービスにsecret keyが要り、DBとStorageに触れるのはapiだけという境界が崩れる。
- 推論サービスが完成時にapiへ送る：送れなかったときに結果を失う。
- 推論サービスから画像を直接配る：スマホから推論サービスに届かせる必要があり、トークンを画面に出せない。
- テクスチャ用の別テーブルを作る：服の削除と画像の取得を別に作る必要がある。`garment_images`のroleにすれば、今の処理がそのまま使える。

## 影響

推論サービスに状態のAPIが入るまでは、推論サービスが404を返すので、状態は常に「まだ作っていない」になる。

裏面を差し替えた直後、古い作業の完成から新しい作業の開始までの間に聞かれると、古い写真のテクスチャを保存することがある。新しい作業が完成すれば差し替わる。

2048pxのテクスチャはPNGで8MiBを超えることがあるため、Storageの1ファイルの上限を16MiBに上げた。利用者が上げる写真は、apiが別に8MiBまでに抑える。

テクスチャのUVがアプリのglbと合うかは、まだ確かめていない。
