# テクスチャを作るときは、同じ写真を切り抜いたときの範囲・点・服の領域を使い回す

日付：2026-10-18

## 背景

テクスチャ1件に約60秒かかっていた。工程ごとに測ると、表と裏の写真それぞれで服の検出（Grounding DINO）に約24秒、ランドマーク（HRNet）に約1.5秒、GrabCutに約3秒かかり、合わせて全体の9割を超えていた。

どちらの写真も、登録の前に同じ推論と切り抜きを済ませている。採寸では`/detect`の`imageBase64`を、裏面では`/detect`に送ったファイルを、そのままStorageに保存する。テクスチャの作業はStorageの写真を受け取るので、同じ推論を2回している。

## 決定

推論サービスは、`/detect`の切り抜きの段階で点を受け取ったら、服の範囲・点・A4の角・服の領域を、写真のJPEGのSHA-256に結び付けて`apps/inference/.cache/detections/`に残す。テクスチャの作業は、受け取った写真のハッシュ・大きさ・服の種類が同じ記録があれば、それを使い、推論と切り抜きをやり直さない。なければ今までどおり推論する。記録は新しいものから200件まで残す。

記録の`.json`には、服の領域の`.png`のSHA-256も残し、読むときに照合する。テクスチャの作業は`/detect`のロックの外で記録を読むので、同じ写真を別の点で切り抜き直している途中だと、新しい`.png`と古い`.json`を組にしてしまうため。合わなければ使わずに推論する。記録は推論を省くためだけのものなので、書けなくても`/detect`は切り抜きの結果を返す。

## 理由

使うのは、利用者が画面で確かめた最後の切り抜きと同じ範囲・点・服の領域なので、テクスチャの結果は推論し直した場合と変わらない。実写のTシャツで、テクスチャ1件が62.5秒から2.1秒になった。色の差が8を超えたテクセルは0.065%で、GrabCutの結果の揺れの範囲だった。

ハッシュで引けば、apiとDBを変えずに済む。範囲（bbox）はDBに保存していないため、DBから渡すにはmigrationと型の作り直しが要る。写真が1バイトでも違えば記録を使わないので、別の写真の結果を取り違えない。

## 代替案

- apiがDBの点とA4の角を`POST /textures`に送る：範囲と服の領域がDBにないため、検出と切り抜きは残る。
- 範囲と服の領域もDBとStorageに保存する：migration・保存の処理・型が増える。推論サービスのPCだけで閉じる方法で足りる。
- 記録をメモリだけに持つ：推論サービスを再起動すると消え、詳細画面の「テクスチャを作る」で作り直すときに使えない。

## 影響

記録は推論サービスのPCだけにあるので、別のPCで動かす推論サービスや、記録を消したあとは、今までどおり推論する（約60秒）。この決定より前に登録した服も同じ。服の領域の画像は写真を含まないが、`.cache/`はGitで除外して共有しない。
