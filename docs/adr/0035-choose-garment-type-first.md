# 撮影の画面で最初に服の種類を選び、シャツを種類に足す

日付：2026-10-17

## 背景

アバターには、Tシャツ・長そで・シャツ・ズボンの4つの3Dモデルがある（[ADR 0018](0018-longsleeve-from-tshirt.md)、[ADR 0019](0019-shirt-from-casualsuit03.md)）。一方、登録できる服の種類は`short_sleeve_top`・`long_sleeve_top`・`trousers`の3つで、シャツと長そでを見分けられなかった。種類は写真から自動で分類していたが、DeepFashion2にシャツのカテゴリはなく、襟付きのシャツも長そでになる。

## 決定

- 撮影の画面では、写真を選ぶ前に「シャツ」「長そで」「Tシャツ」「ズボン」から種類を選ぶ。種類を選ぶまで写真は選べない。選んだ種類で服を検出し、自動の分類は使わない
- 服の種類（`category`）に`shirt`を足す。点・寸法の定義は長そでと同じにする。apiは推論サービスへ`long_sleeve_top`として送り、結果の種類を`shirt`に戻す。推論サービスは変えない
- 種類と3Dモデルの対応は、webの`categoryModels`に置く。アバターが登録した服を読むとき（#70）は、この表で3Dモデルを選ぶ
- シャツのテクスチャは作らない。UVテンプレートがないため、apiは生成の依頼を400で断り、画面ではテクスチャの案内を出さない（その後、[ADR 0037](0037-shirt-texture-from-projected-uv.md)でテンプレートを作り、ほかの種類と同じく作るようにした）

## 理由

着せる3Dモデルは、写真から自動では決められない。シャツと長そでは、DeepFashion2では同じカテゴリだからである。撮る人は服の種類を知っているので、最初に選んでもらえば迷わない。種類が先に決まると、検出もその種類に絞れる。

種類を1つの列で持てば、画面・API・DBで同じ値を使える。種類を足したときは、`Record<Category, …>`の表が型エラーで足りない所を教えてくれる。

## 代替案

- 種類は3つのまま、3Dモデルを別の列に持つ：推論やテクスチャには触れずに済む。ただ、種類と3Dモデルの2つを持つことになり、長そでの服にシャツのモデルを付けるような食い違いが起きうる
- 写真から自動で分類し、違うときだけ撮った後に選び直す（これまでの方法）：シャツを見分けられない

## 影響

- 既存のDBには、カテゴリの制約を広げるmigration（`20261017000400_shirt_category.sql`）が必要
- 撮影の後に種類を変えると、これまでどおり、その種類で点を測り直す
- `Category`を使う表には`shirt`が要る。アバターへ服を渡す`outfitSlot`（`apps/web/src/lib/outfit.ts`）では、シャツを上の服にした
- 画面の表示を「パンツ」から「ズボン」に変えた。推論サービスが作るテクスチャのフォルダ名は「パンツ」のまま
